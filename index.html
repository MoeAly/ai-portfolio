An agent I broke, diagnosed and rebuilt with an independent reviewer

An unattended agent that reads a campaign's live report and media plan, pulls the data, and drafts the client summary. Its first test run had a one-purchase mismatch a client could spot. I traced it to two source tables being mixed, and redesigned it so the AI no longer does arithmetic.

Fix 1One source table for the headline and every split, so all breakdowns add up.
Fix 2A calculator script, and a checker that fails any number not in its table.
Fix 3A reviewer agent with no access to the author's numbers recomputes at least five from the database.

How I instruct AI

Context and instruction design

Real lines from the skills on this page, client names removed. Good instructions are not clever wording: they give the model a rule for every judgment call, and make the important rules impossible to break.

A tie-breakerAccuracy first. A missing number is acceptable; a wrong number is not.

Why: when the model is unsure whether to fill a gap, this one line decides for it, in the safe direction.

An enforced ruleNarrative text uses {tokens} from facts.txt; build_deck.js rejects literal numbers.

Why: "don't invent numbers" is a request. A builder that refuses any typed number makes it a guarantee.

A stop conditionIn a scheduled run, never guess: stop, and send the [BLOCKED] draft listing the question.

Why: an unattended agent has nobody to ask. It must fail loudly instead of guessing quietly.

A reviewer briefYou did not build it. Assume it can be wrong. Work only from the files; do not trust anything you remember from building it.

Why: a model reviewing its own work tends to approve it. Separate context and a sceptical brief stop that.

v1 · What went wrongTotal taken from one data table, breakdowns from another. The total said 44; the breakdown added up to 45.

The model chose its sources freely, and the numbers stopped agreeing.

v2 · The rule that fixed it (simplified)Use one source table for the total and every breakdown.

One explicit source rule, plus a script that checks every breakdown adds up to the total.

Testing 01Real data, real failures

Every build is tested on real data. Failed outputs are kept as test cases: the old faulty version must now fail the checks.

Testing 02Control totals

Each data file is compared with a separate totals query, so a copying slip stops the run.

Testing 03Independent recompute

The reviewer recomputes at least five numbers from raw data. Any mismatch is a fail.

Testing 04Known limits, written down

Each build ships with a list of what is untested or could slip through, and which check backs it up.
